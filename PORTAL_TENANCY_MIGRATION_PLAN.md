# Portal Tenancy Migration Plan

**Status:** Design doc only. No implementation yet. Awaiting approval.
**Scope:** Minimum viable multi-tenancy for internal-tool launch.
**Author:** 2026-04-23
**Tracks:** P0-4 (portal tenancy collapsed). Retires the Phase 2-0 duct-tape (migration 027).
**Out of scope:** email invitations, complex RBAC, Stripe, tenant branding — see §14.

---

## 1. Current state analysis

### 1.1 Hardcoded `demo-tenant-000` in production code

One production reference:

- `backend/app/api/routes/portal_projects.py:34` — `_PORTAL_TENANT_ID = "demo-tenant-000"` module constant.
- `backend/app/api/routes/portal_projects.py:101` — `tenant_id=_PORTAL_TENANT_ID` in `ProjectORM(...)` on project creation.

One seed:

- `backend/migrations/versions/027_seed_demo_tenant.py:36` — idempotent `INSERT INTO tenants (...) VALUES ('demo-tenant-000', ...) ON CONFLICT DO NOTHING`. Explicitly marked "REMOVE after PORTAL_TENANCY_MIGRATION_PLAN.md is executed" (line 12).

All other portal routes derive scope from the authenticated user id, not from a hardcoded tenant.

### 1.2 Portal endpoints — tenancy scoping today

| Route | Method | Current scoping | Problem |
|---|---|---|---|
| `/portal/projects` | GET | `portal_user_id = user.id` | None (user-scoped) |
| `/portal/projects` | POST | Writes `tenant_id=demo-tenant-000` | **P0-4 site.** All projects land in one tenant. |
| `/portal/projects/{id}` | GET / PATCH / DELETE | Ownership via `_own_project` (`portal_projects.py:61`) | None |
| `/portal/projects/{id}/keys` | GET / POST / DELETE | Ownership + `portal_user_id` | Inherits shared tenant_id at insert |
| `/portal/me` + `/portal/me/*` | all | `user.id`-scoped | None |
| `/portal/me/usage` | GET | joins on `api_keys.portal_user_id == user.id` | None |
| `/portal/me/transactions` | GET | `credit_transaction.user_id == user.id` | None |
| `/portal/billing/packs` | GET | **no tenant filter** | Not a leak — token packs are global SKUs. Flagged in §15 Q1. |
| `/portal/billing/purchase` | POST | **no tenant filter** | Same — pack lookup is global. Debit lands on `user.id`. |

Verdict: only one write site hardcodes the tenant. Read-side isolation is already achieved via `portal_user_id`. Fixing the write site + wiring a tenant claim into the portal session addresses the structural problem.

### 1.3 Row counts today

The migration will need to act on:

| Table | Rows tied to `demo-tenant-000` |
|---|---|
| `tenants` | 1 row (the seed) |
| `projects` | Every portal-created project since Phase 2-0 |
| `api_keys` | Every portal-created key (inherits `tenant_id` from its project) |
| `request_logs` | Every request made by any portal-issued key |

Exact counts to be taken on the target DB during cutover prep (see §4). Dev DB has low volume; prod internal usage is the gating factor.

### 1.4 Portal user + session today

- `backend/app/models/portal_user.py` — **no `tenant_id` column.** 41 lines; columns: `id, email, password_hash, display_name, credit_balance, credit_used, plan, status, email_verified, oauth_*, avatar_url, timestamps`.
- Portal JWT payload (`auth_service._mint_token`): `sub, email, type, token_use, iat, exp, jti`. **No `tenant_id` claim.**
- Admin session (`session_manager.create_session`): payload **includes** `tenant_id`. This is what we'll mirror (see §5).

### 1.5 Data model tenancy columns

| Table | `tenant_id` | FK | Index |
|---|---|---|---|
| `tenants` | PK `String(36)` | — | PK |
| `projects` | yes | FK → tenants | yes |
| `api_keys` | yes | FK → tenants | yes |
| `portal_users` | **missing** | — | — |
| `request_logs` | yes | **no FK** | yes |

Two gaps: `portal_users.tenant_id` missing, `request_logs.tenant_id` has no FK. §3 addresses both.

## 2. Target state (internal-tool scope)

1. Every portal user has exactly one `tenant_id`, assigned at signup or when accepting an invite. Multi-tenant membership is out of scope for launch.
2. Signup creates a new tenant + owner user in a single transaction. First user in a tenant is the owner.
3. Additional users join an existing tenant by redeeming an invite code (generated by a tenant owner, copy-pasted through any channel — Slack, email, in-person).
4. Portal session carries `tenant_id`. Every portal write derives tenant scope from the session, not from hardcoded constants or request body.
5. `_PORTAL_TENANT_ID = "demo-tenant-000"` is deleted.
6. Existing `demo-tenant-000` data is preserved by renaming that tenant to a real "Default Team" tenant (§4 Option C). No row-level data migration of `projects`/`api_keys`/`request_logs` is needed.
7. Roles inside a tenant: two only — `owner` and `member`. `owner` can invite + remove members. `member` can CRUD their own projects.

Explicitly **not** in target state for internal-tool launch:
- Email-delivered invitations (§8)
- Onboarding wizard / branded tenant pages (§14)
- Tenant transfer, archive, soft-delete (§14)
- Cross-tenant user membership (§14)

## 3. Data model changes

### 3.1 Schema additions — migration `029_portal_tenancy`

**`portal_users`**
- Add `tenant_id String(36)` — **nullable initially**, FK → `tenants.tenant_id`, `ON DELETE RESTRICT`. Backfill in the same migration (§4), then flip to `NOT NULL` in migration `030` once all rows are populated. Two-step to keep the cutover atomic and reversible.
- Add `tenant_role String(16)` — `'owner' | 'member'`, server default `'member'`. Owner is set explicitly on tenant creation.
- Add composite index `(tenant_id, created_at DESC)` for tenant-member listings.

**New table `tenant_invites`**
```
id            String(36)   PK
tenant_id     String(36)   FK → tenants, ON DELETE CASCADE, INDEXED
code          String(64)   UNIQUE NOT NULL       -- opaque token, url-safe
created_by    String(36)   FK → portal_users.id, NOT NULL
created_at    TIMESTAMPTZ  DEFAULT now()
expires_at    TIMESTAMPTZ  NOT NULL              -- default now() + 7d
used_at       TIMESTAMPTZ  NULL                  -- single-use when set
used_by       String(36)   FK → portal_users.id  -- redeeming user
email_hint    TEXT         NULL                  -- optional display hint only
```
Partial unique index on `(code) WHERE used_at IS NULL` to make redemption lookups fast.

**`request_logs`**
- Add FK constraint `tenant_id` → `tenants.tenant_id`, `ON DELETE RESTRICT`. No data change; just closes the gap from §1.5. Defer to a follow-up migration if any existing row violates the constraint — see §12 risk R3.

### 3.2 Constraint semantics

- `ON DELETE RESTRICT` on every tenant FK: tenant deletion requires the operator to explicitly clean up or reassign. No cascading wipes.
- `ON DELETE CASCADE` on `tenant_invites.tenant_id`: invites are ephemeral, no reason to preserve them past their tenant.
- Invite `code` is generated server-side via `secrets.token_urlsafe(32)`. Never derived from user-supplied input.

## 4. Migration strategy for existing data

**Recommendation: Option C** (preserve + rename).

### Option C — primary plan

1. `UPDATE tenants SET name = 'Default Team', slug = 'default-team' WHERE tenant_id = 'demo-tenant-000'` — same row, reframed as a real tenant. The stable primary key `demo-tenant-000` stays, which means no `projects`/`api_keys`/`request_logs` rewrites are needed.
2. Backfill every existing `portal_user` with `tenant_id = 'demo-tenant-000'`, `tenant_role = 'member'`.
3. Promote the oldest-created portal user to `tenant_role = 'owner'`. If zero portal users exist, leave it ownerless — first post-migration signup takes ownership (edge case §12 R4).
4. In a later migration (`030`), flip `portal_users.tenant_id` to `NOT NULL` and drop the demo-tenant seed (migration 027 contents become redundant).

**Why C**: zero row rewrites across the largest tables (`request_logs`), zero user-visible disruption, reversible by re-running migration 029's downgrade. Stable tenant_id means no invalidation of existing API keys or logged request traces.

### Option A — "one tenant per existing user"

Create N new tenants, one per user, and rewrite every `projects.tenant_id`, `api_keys.tenant_id`, `request_logs.tenant_id` to match. Rejected for internal tool: high row-count impact on `request_logs`, breaks every existing API key's tenant context mid-flight, and we don't need per-user isolation between teammates who today share `demo-tenant-000`.

### Option B — "prompt on next login"

Leave users in limbo until they log in, then modal them to create/join. Rejected: partial state in the DB indefinitely, hard to reason about tenant-scoped queries ("is this user's `tenant_id` null or real?"), bad UX for an internal tool where we control who logs in.

### Cutover checklist (Option C)

- [ ] Take DB snapshot (logical `pg_dump` + cold snapshot of PVC).
- [ ] Announce maintenance window to internal users.
- [ ] Run `alembic upgrade 029`.
- [ ] Verify: every `portal_users` row has `tenant_id = 'demo-tenant-000'`, exactly one has `tenant_role = 'owner'`.
- [ ] Smoke-test: portal login → projects list → create project (must not hit the dropped `_PORTAL_TENANT_ID` constant — that code path is replaced in the same release).
- [ ] Rollback path documented in §10.

## 5. Code changes required

### 5.1 Backend — new pieces

- **`app/services/portal/tenant_service.py`** (new): `create_tenant_with_owner`, `generate_invite`, `redeem_invite`, `list_members`, `remove_member`. Pure ORM operations; no HTTP concerns.
- **`app/services/portal/auth_service.py`**: extend JWT payload to include `tenant_id` + `tenant_role`. Bump a token version claim so existing portal JWTs are invalidated cleanly on deploy (forces a fresh login, one-time user friction).
- **`app/api/deps.py::get_portal_user`**: already loads the ORM row from DB, so adding tenant context is a read of the already-loaded user. Add a companion `get_portal_tenant_context() -> (tenant_id, role)` dep for route signatures that prefer the tuple.
- **`app/api/admin_auth.py`**: consider factoring `@scope_to_tenant` into a shared module (`app/api/scope.py`) so a portal analogue can reuse the signature-rewrite trick without duplicating code. Non-blocking; we can also write a parallel `@scope_to_portal_tenant` and DRY later.

### 5.2 Backend — edits

- **`app/api/routes/portal_projects.py`**:
  - Delete line 34 (`_PORTAL_TENANT_ID`).
  - Replace line 101 with `tenant_id=user.tenant_id` (after `PortalUserORM.tenant_id` exists).
  - Every write (`create_project`, key creation) reads tenant from the session-loaded user, never from request body.
- **`app/api/routes/portal_auth.py`**: signup endpoint must create tenant + user atomically. Add `/portal/invites/redeem` taking an invite code.
- **`app/api/routes/portal_team.py`** (new): `GET /portal/team/members`, `POST /portal/team/invites`, `DELETE /portal/team/invites/{id}`, `DELETE /portal/team/members/{id}`. Owner-only for the mutating routes (enforced via `tenant_role == 'owner'` check).

### 5.3 Admin UI + Portal UI

- **Portal signup page**: unchanged flow for "create new account" (implicitly creates a tenant). Add a sibling "I have an invite code" field.
- **Portal team page** (new, minimal): shows members list + pending invites + "generate invite code" button that displays the code inline for copy-paste. Owner-only actions gated by the `tenant_role` claim.
- **Admin UI**: not touched by this refactor. Admin already has multi-tenant support from Phase 2A.

### 5.4 Deletions

- `_PORTAL_TENANT_ID` constant.
- Migration 027's data contract (the row stays via the rename in §4; the migration file itself remains in history but its logic is superseded).

## 6. API contract changes

### 6.1 Breaking changes

- **Portal JWT**: new claims `tenant_id`, `tenant_role`. Existing tokens keep validating (claims default to `None`), but write endpoints will 403 without a tenant claim. Force re-login on deploy by bumping a token version claim.
- **`POST /portal/projects` response**: unchanged shape; `tenant_id` field already exists in `_to_dict` (`portal_projects.py:53`) but previously always returned `demo-tenant-000`. Now returns the real per-user tenant.
- **`GET /portal/me` response**: add `tenant_id` and `tenant_role` fields. Additive, non-breaking.

### 6.2 Deprecation strategy

Internal tool = we control the clients. One-line notice in #eng, force re-login at deploy, done. No multi-version shim needed.

## 8. Email integration — deferred for launch

Invite flow **for internal tool launch** uses **invite codes shown in the UI**. Owner clicks "Generate invite", UI displays a one-time code, owner copies it into Slack/email/wherever. Invitee pastes it on the portal signup page.

Trade-off (explicit): no email verification of the *inviter*, no "email-as-identity" binding on the invite. The `email_hint` column on `tenant_invites` is display-only — it's not enforced at redemption. An attacker with a leaked invite code can redeem it under any email. Mitigations:
- Invite codes are 43 chars of entropy (`secrets.token_urlsafe(32)`).
- 7-day expiration; single-use.
- Owner-only generation, logged in `admin_audit_log`.

Real email delivery (transactional provider, templated invite email, verified inviter) is tracked as a Phase 3 enhancement. Replacement is non-breaking — same endpoints, code delivery via email instead of copy-paste.

## 9. Testing strategy

### 9.1 Unit tests
- `test_portal_tenant_service.py`: tenant creation, invite generation uniqueness, invite redemption idempotency (double-redeem → 409), expired invite → 410 Gone, owner promotion on first user.
- `test_portal_jwt_tenant_claim.py`: JWT carries `tenant_id`, malformed claim → 401, missing claim after deploy → 403 with `reauth_required`.

### 9.2 Integration tests
- **Two-tenant isolation**: User A creates project in tenant T1. User B (separate tenant T2) cannot see T1's projects via any portal endpoint. Assert this for every GET/LIST route, not just projects.
- **Invite round-trip**: User A creates tenant, generates invite, User B redeems, both see tenant in `/portal/team/members`.
- **Owner-only gates**: Member attempts to generate invite → 403. Member attempts to remove another member → 403.
- **Signup creates real tenant**: fresh DB, signup, verify a new row lands in `tenants` with the user as owner.

### 9.3 Migration test
- Apply migration 029 to a snapshot with N portal users + M projects. Assert: every user has `tenant_id='demo-tenant-000'`, oldest user is `owner`, no `projects`/`api_keys`/`request_logs` rows modified. Downgrade path restores pre-migration state.

### 9.4 Regression
- Full Phase 2A + 2B + 2C test suite (160 tests) continues to pass unchanged. Tenancy refactor must not touch admin auth surface.
- Counts / unicode / upload tests from Phase 1.4 unchanged.

## 10. Rollout plan

1. **Staging**: merge → deploy to audit stack (5433/6380/8090). Run full suite. Manually exercise signup + invite.
2. **Snapshot prod**: `pg_dump` + PVC snapshot immediately before maintenance window.
3. **Maintenance window**: announce 30-min window in #eng. Internal users only, low-risk.
4. **Deploy**: `alembic upgrade 029`, roll backend, roll portal frontend. Force portal re-login via token-version bump.
5. **Smoke**: admin observes `/portal/projects` creation now writes real tenant_id (`SELECT DISTINCT tenant_id FROM projects WHERE portal_user_id IS NOT NULL` — should show more than one value within a few minutes of user activity).
6. **Monitor**: 48h watch on tenant count growth, invite redemption success rate, any cross-tenant 403s in portal logs (would indicate a bug, not a breach).

### Rollback
- `alembic downgrade 028` restores the schema.
- Portal frontend rollback restores the signup flow.
- No data loss: Option C's rename is reversible (`UPDATE tenants SET name='Demo Tenant', slug='demo' WHERE tenant_id='demo-tenant-000'`), new tenant rows from post-migration signups need case-by-case handling — if any new tenants were created in the <30min window, they'd be orphaned on rollback. Acceptable for internal tool.

## 12. Risks + mitigations

| # | Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|---|
| R1 | Migration corruption on backfill | Low | High | Snapshot + downgrade test on snapshot before prod run |
| R2 | Users locked out mid-deploy | Medium | Medium | Force re-login is expected UX; 30-min window announced |
| R3 | Orphaned `request_logs.tenant_id` breaks new FK | Medium | Low | Pre-migration scan: `SELECT COUNT(*) FROM request_logs WHERE tenant_id NOT IN (SELECT tenant_id FROM tenants)`. If >0, insert a `tenants` row with the missing id before the FK lands. |
| R4 | Zero existing users at cutover → no owner | Low | Low | First post-migration signup takes ownership of demo-tenant-000; subsequent signups create new tenants. Requires one conditional branch in the signup service. |
| R5 | Cross-tenant leak in route not caught by tests | Medium | High | Integration test template that iterates every portal route and verifies T2 cannot see T1 data; template applied exhaustively, not per-route |
| R6 | Portal JWT claim drift (existing tokens accepted) | Medium | Medium | Token version claim; reject all tokens minted before the cutover version |
| R7 | Invite code phishing (attacker intercepts) | Medium | Medium | 7-day expiry + single-use + owner audit trail. Real email + inviter verification is Phase 3. |
| R8 | Admin session doesn't already carry tenant_id correctly post-refactor | Low | High | Admin side is not touched; run Phase 2A 160-test regression after every commit |

## 14. Deferrals (post-launch)

Explicitly **out** of this refactor:

- Email-delivered invitations + inviter email verification
- Onboarding wizard for new tenants
- Tenant settings page (name, logo, avatar, billing address)
- Complex role hierarchy beyond `owner`/`member` (e.g., `billing_admin`, `viewer`)
- Cross-tenant user membership (one user → multiple tenants)
- Tenant transfer, merge, archive, soft-delete
- Per-tenant branded portal URLs (custom subdomains)
- Per-tenant policy profiles (currently one global pool)
- Tenant-scoped token packs / pricing tiers (triggers the §1.2 billing question)

Everything above extends cleanly from the schema in §3. None of it changes the migration path; all of it can be layered on once the foundation is in.

## 15. Open questions for Beat

1. **Token packs**: `portal_billing.list_packs` returns all active packs globally. Is this correct (global SKUs, everyone sees the same prices) or should packs become tenant-scoped (per-tenant pricing)? Answer changes whether §3's schema needs a `token_packs.tenant_id` nullable column. Default assumption: global SKUs, no change needed.
2. **Invite expiration default**: 7 days proposed. Is that right for internal tool (where invites often pass informally) or should we go shorter (24h) / longer (30d)?
3. **Orphan ownership**: if a tenant owner leaves the company, what's the recovery path? Options: (a) admin-side reassignment via admin UI; (b) portal "transfer ownership" endpoint owner-only; (c) defer. Default assumption: defer (§14) — internal tool, hand-fix in DB if it happens.
4. **First-user-is-owner at signup**: confirmed? Or should signup always ask "create new tenant OR have invite code" — no implicit tenant creation? Default assumption: implicit tenant creation, same as existing signup UX.
5. **Demo tenant name**: "Default Team" proposed for the renamed `demo-tenant-000`. Any preferred alternative ("Seed Team", company name, etc.)?
