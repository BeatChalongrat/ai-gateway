# ดีไซน์ที่เสนอ — `open_application` (P3-6)

> **สถานะ: ข้อเสนอ ยังไม่เขียนโค้ด** ตามที่สั่งไว้ใน P3
> ทุกข้อความในหัวข้อ "สภาพปัจจุบัน" อ้าง `path:line` จริง

---

## 1. สภาพปัจจุบัน — [ข้อเท็จจริงจากโค้ด]

`OpenApplicationTool.ExecuteAsync` มีสองเส้นทางที่แยกกันอยู่แล้วในโค้ด
แต่ผูกกันด้วยพารามิเตอร์ `name` ตัวเดียวและคำอธิบาย tool อันเดียว

| เส้นทาง | บรรทัด | ข้อจำกัดจริง |
|---|---|---|
| **Focus** หน้าต่างที่เปิดอยู่ | `OpenApplicationTool.cs:52-60` | **ไม่มีเลย** — `Win32Input.FindWindowByTitle(name)` รับ title อะไรก็ได้ |
| **Launch** โปรแกรมใหม่ | `:62-92` → `TryResolveTrustedApplication` `:97-120` | allowlist 3 ไฟล์: `notepad.exe`, `calc.exe`, `mspaint.exe` (`:12-20`) |

### สิ่งที่พบและน่าจะไม่มีใครตั้งใจ

**ก. เส้นทาง focus ไม่ถูกจำกัดอยู่แล้ว**
`:52` รันก่อน `:62` เสมอ ดังนั้น "โฟกัสหน้าต่างชื่อ Visual Studio Code" **ทำงานได้วันนี้**
แต่ `Description` (`:26-28`) บอกว่า *"Focus an existing window by title, or launch trusted
Notepad, Calculator, or Paint"* ซึ่งอ่านแล้วเหมือน Chrome/Excel/VS Code ทำอะไรไม่ได้เลย
→ **ความสามารถมีอยู่ แต่โมเดลไม่รู้ว่ามี** ไม่ใช่เรื่องความปลอดภัย เป็นเรื่อง discoverability

**ข. `TryResolveTrustedApplication` ปฏิเสธชื่อที่มีช่องว่าง**
`:107` `normalized.Any(char.IsWhiteSpace)` → `"Visual Studio Code"` ตกตั้งแต่ยังไม่ถึง allowlist
เขียนไว้เพื่อกัน argument injection ซึ่งถูก แต่มันหมายความว่า **ต่อให้ขยาย allowlist
ในรูปแบบปัจจุบัน ชื่อแอปที่มีช่องว่างก็ยังเข้าไม่ได้อยู่ดี** — ต้องแก้ทั้งคู่ ไม่ใช่แค่เติมตาราง

**ค. allowlist ผูกกับ `System32` เท่านั้น**
`:111-116` resolve จาก `Environment.SpecialFolder.System` แล้วตรวจว่าไม่หลุดออกนอก
→ โครงสร้างนี้รองรับได้เฉพาะโปรแกรมที่อยู่ใน System32 เท่านั้นโดยการออกแบบ
Chrome (`C:\Program Files\Google\...`) และ Excel (`C:\Program Files\Microsoft Office\...`)
เข้าไม่ได้แม้จะเติมชื่อลงตาราง

## 2. ข้อเสนอ

### เฟส A — แยก focus ออกจาก launch (ทำได้เลย ความเสี่ยงเพิ่ม = ศูนย์)

**ปัญหาที่แก้:** ความสามารถที่มีอยู่แล้วแต่ไม่มีใครรู้

- แยกเป็นสอง tool: `focus_window` (focus อย่างเดียว) กับ `open_application` (launch)
  หรืออย่างน้อยแยก parameter: `window_title` กับ `application`
- `focus_window` — ไม่ launch อะไรเลย ผลลัพธ์คือหน้าต่างที่มีอยู่แล้วขึ้นหน้า
  ยัง verify HWND/PID/foreground เหมือนเดิม (`VerifiedWindowResultAsync`)
- `Description` บอกตรง ๆ ว่า focus ได้ทุกหน้าต่าง แต่ launch ได้เฉพาะรายการที่อนุญาต

**กลไกที่มาแทนข้อจำกัด:** ไม่มีข้อจำกัดไหนถูกถอด — เส้นทางนี้ไม่ได้ถูกจำกัดตั้งแต่แรก
สิ่งที่เปลี่ยนคือโมเดลรู้ว่าเรียกได้ ความเสี่ยงของการโฟกัสหน้าต่างที่ผู้ใช้เปิดเอง
อยู่ที่ *สิ่งที่ทำต่อจากนั้น* (`computer_type` / `uia_set_value`) ซึ่งมี consent + verification
ของตัวเองอยู่แล้ว

> **⚠️ ข้อควรระวังจากเหตุการณ์จริง:** เคยมีครั้งที่ smoke test พิมพ์ทับไฟล์ `ssh.txt`
> ใน Notepad ที่ผู้ใช้เปิดค้างไว้ การทำให้ focus เข้าถึงง่ายขึ้น **เพิ่มโอกาสเจอเคสแบบนี้**
> เฟส A จึงควรมาพร้อมกฎว่า focus หน้าต่างที่แอปไม่ได้เปิดเอง ต้องนับเป็น
> `ForegroundTargetTracker` target ที่ต้องขอ consent ก่อนพิมพ์ ไม่ใช่แค่ก่อนโฟกัส

### เฟส B — ขยาย launch ด้วยหลักการ ไม่ใช่ตารางฝังตาย

เสนอ resolve 3 ชั้น เรียงตามความเข้มของหลักฐาน:

| ชั้น | ที่มาของ path | ตรวจอะไร | ตัวอย่าง |
|---|---|---|---|
| 1 | allowlist System32 เดิม | เหมือนเดิมทุกอย่าง | notepad, calc, mspaint |
| 2 | `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\App Paths\<name>.exe` | ต้องเป็น `HKLM` เท่านั้น (ไม่ใช่ `HKCU` ซึ่งเขียนได้โดยไม่ต้อง admin) + Authenticode signature valid + publisher อยู่ใน trusted publisher list | chrome, msedge, code |
| 3 | ผู้ใช้เพิ่มเองใน Settings | ผู้ใช้เลือกไฟล์ `.exe` ด้วย file picker → เก็บ path + hash ตอนเพิ่ม → ตรวจ hash ทุกครั้งก่อน launch | อะไรก็ได้ที่ผู้ใช้ยืนยัน |

**สิ่งที่ต้องแก้พร้อมกัน:** `:107` กฎ "ห้ามมีช่องว่าง" ต้องเปลี่ยนเป็น
"ชื่อถูก resolve เป็น path แล้วเท่านั้นจึงส่งต่อ ไม่เคยส่ง raw string เข้า shell"
— ปัจจุบัน `:67` ใช้ `UseShellExecute = false` + path เต็มอยู่แล้ว ซึ่งถูก
กฎห้ามช่องว่างจึงกันสิ่งที่กันไปแล้ว และกัน Chrome ทิ้งไปด้วยเป็นผลข้างเคียง

**ทำไมต้องเป็น HKLM + signature ไม่ใช่แค่ App Paths:**
`HKCU\...\App Paths` เขียนได้โดยไม่ต้องสิทธิ์ admin ถ้ายอมรับชั้นนั้น มัลแวร์ที่รันในสิทธิ์
ผู้ใช้เดียวกันสามารถลงทะเบียน `chrome.exe` ชี้ไปที่อะไรก็ได้ แล้วรอให้ agent เรียก
signature check ปิดช่องนั้นเพราะ path ที่ถูกสลับจะไม่มีลายเซ็นของ Google

### สิ่งที่ยังไม่มีคำตอบ ต้องตัดสินใจก่อนเขียน

1. **trusted publisher list มาจากไหน** — hardcode (Microsoft, Google, Mozilla, JetBrains…)
   หรือ "publisher ใดก็ได้ที่ signature valid" อย่างหลังกว้างกว่ามาก มัลแวร์เซ็นชื่อตัวเองได้
   ถ้าซื้อ cert — เสนอ: hardcode ก่อน + ให้ผู้ใช้เพิ่มผ่านชั้น 3
2. **ชั้น 3 ต้อง re-verify hash ทุกครั้งไหม** — โปรแกรมอัปเดตตัวเองแล้ว hash เปลี่ยน
   จะกลายเป็นถามซ้ำทุกครั้งหลัง Chrome อัปเดต เสนอ: ถ้า hash เปลี่ยนแต่ signature
   ยังเป็น publisher เดิม → ผ่านและอัปเดต hash ที่เก็บไว้ ถ้า signature เปลี่ยน → ถามใหม่
3. **consent ระดับไหน** — `Ask` ทุกครั้ง หรือจำต่อแอป เสนอ: จำต่อแอปได้
   แต่ชั้น 3 ที่เพิ่งเพิ่มต้องถามครั้งแรกเสมอ

## 3. ลำดับที่แนะนำ

1. **เฟส A** — คุ้มที่สุดต่อ effort และไม่ถอดข้อจำกัดอะไรเลย
   ต้องทำคู่กับกฎ consent ตอนพิมพ์ในหน้าต่างที่แอปไม่ได้เปิดเอง
2. **เฟส B ชั้น 3** (ผู้ใช้เลือกเอง) ก่อนชั้น 2 — ผู้ใช้เลือกไฟล์เองคือหลักฐานที่หนักที่สุด
   และไม่ต้องเถียงเรื่อง trusted publisher list
3. **เฟส B ชั้น 2** (App Paths + signature) ท้ายสุด เพราะต้องตอบคำถาม 3 ข้อข้างบนก่อน
